# Plan

## Goal
Build a Python backend that receives and stores HTTP traffic logs generated by user-device agents for security analysis.

## Scope
- authenticate users and agents
- accept traffic log data through a secure HTTP API
- store normalized data in MongoDB
- enforce access restrictions and redact sensitive information
- support local development and containerized deployment

## Architecture
- `app/main.py`: FastAPI app and route registration
- `app/api`: request handlers
- `app/services`: domain logic and orchestration
- `app/db`: MongoDB access and persistence
- `app/core`: config, security checks, and logging
- `tests/`: validation for auth, traffic ingestion, and security policies

## Decisions
- Python and FastAPI are the default stack for the project.
- MongoDB is the persistence layer.
- Sensitive fields are redacted before logging or storage.
- Raw request bodies are represented by byte length and SHA-256 digest to minimize sensitive data.
- The versioned REST API exposes batch ingestion, owner-scoped log collection/item
  reads, and the current authenticated identity. Auth0 remains the authorization
  server; the backend never issues local tokens.
- Agents upload gzip-compressed JSON batches: 1-500 records, at most 1 MiB compressed
  and 8 MiB expanded. Validation and whole-batch ownership checks precede publishing.
- Logs use `traffic_logs`, a MongoDB time-series collection with `timestamp` as
  `timeField`, `metadata` as `metaField`, and `seconds` granularity. Stable metadata
  contains only user and device identity; batch IDs remain measurement fields.
- Traffic records are indexed by user/device plus event time and record ID, and by
  ingestion time. Analysis pagination uses timestamp/ID keysets, not growing offsets.
- Writes use primary with majority write concern. Analysis uses strict `SECONDARY`
  read preference with majority read concern; lack of a secondary is an explicit
  availability error, never a primary fallback. Single-node local development can
  explicitly select primary analysis; this option is rejected outside development.
  Replication lag is visible to deployment clients.
- A replica-set URI is mandatory, and direct connections are rejected.
- The authenticated token subject must match the submitted traffic log user.
- Auth and authorization checks are mandatory for protected routes.

## Queue boundary

`IngestionPublisher.publish(batch_id, documents)` is the batch ingestion handoff.
The service owns authentication, authorization, normalization,
header redaction, body minimization, and ID assignment before that boundary. The
publisher receives no bearer token or raw body. It returns a receipt only after
durable acceptance, or raises `PersistenceError` so the API returns `503`.

The MVP adapter, `MongoIngestionPublisher`, calls the batch writer directly and
acknowledges only majority-persisted writes. No broker or background processing
is deployed in this version.

A future queue adapter should serialize a versioned envelope containing `batch_id`
and the normalized documents (including assigned record IDs and BSON datetimes),
wait for a durable broker acknowledgement, and return `status=queued`. Partition
by authenticated user/device when ordering is needed. A separate consumer writes
to primary through the batch writer; analysis continues to read secondaries.
Consumers acknowledge messages only after durable persistence, use bounded retries,
and route exhausted/invalid messages to an observable dead-letter queue.

Delivery is at-least-once, not exactly-once. MongoDB time-series collections cannot
enforce unique IDs, and bulk writes can partially succeed. Before enabling retries
or a real queue, design an external idempotency/inbox store and recovery procedure;
neither batch IDs nor generated record IDs alone prevent duplicate measurements.
