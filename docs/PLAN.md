# Plan

## Goal
Build a Python backend that receives and stores HTTP traffic logs generated by user-device agents for security analysis.

## Scope
- authenticate users and agents
- accept traffic log data through a secure HTTP API
- store normalized data in MongoDB
- enforce access restrictions and redact sensitive information
- support local development and containerized deployment

## Architecture
- `app/main.py`: FastAPI app and route registration
- `app/api`: request handlers
- `app/services`: domain logic and orchestration
- `app/db`: MongoDB access and persistence
- `app/core`: config, security checks, and logging
- `tests/`: validation for auth, traffic ingestion, and security policies

## Decisions
- Python and FastAPI are the default stack for the project.
- MongoDB is the persistence layer.
- Sensitive fields are redacted before logging or storage.
- Raw request bodies are represented by byte length and SHA-256 digest to minimize sensitive data.
- The versioned REST API exposes batch ingestion, owner-scoped log collection/item
  reads, and the current authenticated identity. Auth0 remains the authorization
  server; the backend never issues local tokens.
- Agents upload gzip-compressed JSON batches: 1-500 records, at most 1 MiB compressed
  and 8 MiB expanded. Validation and whole-batch ownership checks precede publishing.
- Logs use `traffic_logs`, a MongoDB time-series collection with `timestamp` as
  `timeField`, `metadata` as `metaField`, and `seconds` granularity. Stable metadata
  contains only user and device identity; batch IDs remain measurement fields.
- Traffic records are indexed by user/device plus event time and record ID, and by
  ingestion time. Analysis pagination uses timestamp/ID keysets, not growing offsets.
- Writes use primary with majority write concern. Analysis uses strict `SECONDARY`
  read preference with majority read concern; lack of a secondary is an explicit
  availability error, never a primary fallback. Single-node local development can
  explicitly select primary analysis; this option is rejected outside development.
  Replication lag is visible to deployment clients.
- A replica-set URI is mandatory, and direct connections are rejected.
- The authenticated token subject must match the submitted traffic log user.
- Auth and authorization checks are mandatory for protected routes.

## Application encryption and management

- Non-local API traffic requires HTTPS through a trusted TLS gateway; forwarded
  schemes are accepted only from explicitly trusted proxy IPs/CIDRs.
- Per-owner/device configuration lives in the regular `device_configurations`
  collection. Default version zero is `tls_only`; `optional` permits either upload
  format and `required` rejects plaintext. Policy reads use primary/majority for
  enforcement, independently of secondary-only analysis routing.
- `GET /api/v1/devices/{id}/configuration` exposes policy and only the active public
  key. `PATCH` requires `manage:devices` and atomic expected-version matching.
  `PUT /api/v1/devices/{id}/configuration-status` records client capability and
  applied/unsupported/error status, with version and key checks.
- Application-encrypted uploads use JSON -> gzip -> compact JWE,
  a configured ECDH/AES suite (default NIST P-384, ECDH-ES+A256KW, A256GCM),
  `application/jose`, and authenticated protected key IDs and ephemeral public keys.
  Decryption precedes bounded decompression, validation, ownership/policy checks,
  redaction, and the publisher boundary. No opaque encryption crosses that boundary.
- OpenBao Transit wraps the private EC key set using a non-exportable AES-256-GCM
  KEK; KV v2 stores only wrapped ciphertext with compare-and-swap. Runtime credentials
  grant only exact-record read and exact-key decrypt. EC keys are unwrapped into
  backend RAM at startup; JWE/ECDH decryption remains local because Transit does
  not provide ECDH JWE decryption. No plaintext EC files or private EC Secrets are used.
  One active public key is advertised; retained keys decrypt buffered batches.
  Staged rotation/activation and retirement require process restarts. KEK rotation
  rewraps ciphertext without changing client EC keys. Replay deduplication is absent.
- Suite selection lives in environment/Helm configuration and drives key generation,
  client discovery, key validation, and decryption. Only NIST prime-field curves
  and supported ECDH/AES-KW/AES-GCM combinations are accepted. This is classical
  cryptography, not post-quantum protection or a FIPS validation claim.
- Clients must implement configuration polling and encryption support; changing
  backend policy cannot upgrade older agents. Roll out optional encryption first.
  The owner remains the authentication principal; there is no separate device
  enrollment or device-bound credential service.
- See [the encryption protocol](ENCRYPTION.md) for setup, limits, status semantics,
  proxy trust, OpenBao operations, and two-phase key rotation.

## Local development

- Docker Compose runs one MongoDB service as a self-initializing single-node replica
  set with a persistent volume and loopback port 28017. Its healthcheck waits for
  primary readiness; no extra initializer or secondary services are needed.
- Compose also runs one loopback-only, ephemeral OpenBao dev instance on port 28200.
  Bootstrap generates private ignored root/runtime credentials and provisions
  engines, wrapped keys, and least-privilege policy. KMS restarts lose keys; MongoDB
  storage persists. Production requires a separately operated persistent OpenBao.
- `make dev` waits for both dependencies and runs the backend in the host virtual
  environment with Uvicorn reload. `make run` / `python -m app` run Python alone using `.env`;
  neither command builds an application image.
- Compose and Python share a parameterized `.env`, including URI interpolation,
  port 8001 for Python, and an explicit development-only primary-read flag.
- Kubernetes keeps independent Helm values: API pod port 8000, MongoDB pod port
  27017, OpenBao pod port 8200, and local API port-forward 18000.
  Deployment reads stay secondary-only.

## Kubernetes deployment

- `helm/amazing-http-logger` deploys the API as a non-root
  Deployment with resource limits, startup/liveness/readiness probes, no service
  general-purpose service-account token, and a read-only root filesystem. Its Service is ClusterIP.
  A dedicated ServiceAccount and audience-bound projected JWT authenticate to OpenBao.
- By default MongoDB is external and its URI comes from an existing Kubernetes
  Secret. Helm never renders database credentials or stores them in release values.
  Auth0's public tenant/audience settings are stored in a ConfigMap.
- Production defaults to external HTTPS OpenBao with preconfigured Kubernetes auth;
  optional credential/CA Secrets are mounted read-only. No private EC key Secrets
  or production KMS initialization/unsealing are installed by this chart.
- `values-development.yaml` opts into an unauthenticated three-member MongoDB
  StatefulSet with per-member PVCs, stable headless-Service DNS, and an ingress
  NetworkPolicy. It is not a production database deployment.
- The development profile also bundles ephemeral OpenBao, a generated root Secret,
  TokenReview RBAC, and an idempotent bootstrap Job. Only server/bootstrap pods
  mount the root credential; API pods receive least-privilege Kubernetes login.
  Bundled KMS restarts require bootstrap/API rollout and cannot recover lost keys.
- All MongoDB pods start in parallel. The headless Service publishes not-ready
  addresses, allowing initialization before replica-role readiness succeeds.
  A normal, revision-named Job initializes or validates the replica set; it is not
  a post-install hook, which would deadlock Helm's readiness wait.
- API init containers wait for primary connectivity and KMS provisioning. Application lifespan
  still validates time-series storage before the HTTP server starts. Probes are
  process-health checks; loss of a secondary does not prevent primary ingestion.
- Helm deployments rerun the idempotent initialization check. PVCs remain after
  uninstall; use a stable release name and namespace for the development database.

## Queue boundary

`IngestionPublisher.publish(batch_id, documents)` is the batch ingestion handoff.
The service owns authentication, authorization, normalization,
header redaction, body minimization, and ID assignment before that boundary. The
publisher receives no bearer token or raw body. It returns a receipt only after
durable acceptance, or raises `PersistenceError` so the API returns `503`.

The MVP adapter, `MongoIngestionPublisher`, calls the batch writer directly and
acknowledges only majority-persisted writes. No broker or background processing
is deployed in this version.

A future queue adapter should serialize a versioned envelope containing `batch_id`
and the normalized documents (including assigned record IDs and BSON datetimes),
wait for a durable broker acknowledgement, and return `status=queued`. Partition
by authenticated user/device when ordering is needed. A separate consumer writes
to primary through the batch writer; analysis continues to read secondaries.
Consumers acknowledge messages only after durable persistence, use bounded retries,
and route exhausted/invalid messages to an observable dead-letter queue.

Delivery is at-least-once, not exactly-once. MongoDB time-series collections cannot
enforce unique IDs, and bulk writes can partially succeed. Before enabling retries
or a real queue, design an external idempotency/inbox store and recovery procedure;
neither batch IDs nor generated record IDs alone prevent duplicate measurements.
