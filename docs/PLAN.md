# Plan

## Goal
Build a Python backend that receives and stores HTTP traffic logs generated by user-device agents for security analysis.

## Scope
- authenticate users and agents
- accept traffic log data through a secure HTTP API
- store normalized data in MongoDB
- enforce access restrictions and redact sensitive information
- support local development and containerized deployment

## Architecture
- `app/main.py`: FastAPI app and route registration
- `app/api`: request handlers
- `app/services`: domain logic and orchestration
- `app/db`: MongoDB access and persistence
- `app/core`: config, security checks, and logging
- `tests/`: validation for auth, traffic ingestion, and security policies
- `app/api/uploads.py`: durable raw-upload endpoint and receipt status
- `app/services/upload_*`: GCS/MinIO adapter, Pub/Sub, receipts, silver transport and workers
- `app/spool_worker.py`: independently deployable parser/loader plus targeted replay/cleanup CLI

## Upload pipeline decisions

- Authentication, device policies, frontend, Mongo collection/indexes, secondary
  analysis routing and workspace TTL are independent of the upload transport.
- The upload endpoint explicitly acknowledges raw receipt, not validated records.
  Wire-size/transfer-policy checks stay synchronous; JWE/gzip/schema validation
  and field protection reuse the existing implementation in worker #1.
- Production uses GCS OBJECT_FINALIZE -> Pub/Sub. Development uses real MinIO,
  a private notification bridge and the Pub/Sub emulator. AWS is not provisioned.
- This is temporary bronze, not a historical lake/cold tier: delete only after
  majority Mongo persistence and a terminal receipt; failures retain replay source.
  No bucket TTL, versioning or soft-deleted copies are enabled. Receipt state
  is retained for idempotency and operational recovery, not used as the primary trigger.
- Raw storage temporarily includes values the final workspace policy discards.
  A policy snapshot governs worker processing.
  Use synthetic data in the local unencrypted MinIO volume.
- Optional device-scoped X-Batch-Id, unique object keys, conditional object writes,
  stage claims and deterministic record IDs provide layered retry protection.
  Mongo time-series limitations mean ambiguous writes still prevent an exactly-once guarantee.
- A separate Pub/Sub silver topic/subscription buffers normalized protected
  documents, with explicit ACK, deadline redelivery, bounded pull and load DLQ.
  Managed retention is configurable; raw remains available if messages expire.
- Worker #2 limits documents/second per replica, retries writes, routes poison
  work to a Pub/Sub DLQ and ACKs only after success or a durable dead-letter write.
- Production GCP Terraform always provisions the bucket, topics/subscriptions,
  scoped identities, DLQ alerts and two supervised always-on Cloud Run workers.
  Cloud Run services remain gated by `deploy_services`. Helm always deploys the
  same two workers on GKE with workload identity and externally provisioned cloud resources.
- See the README core flow for medallion mapping, latency target, metrics,
  retention and delivery limits.

## Decisions
- Python and FastAPI are the default stack for the project.
- MongoDB is the persistence layer.
- Sensitive captured fields are encrypted before storage by default; credential
  responses and operational logs remain redacted.
- Raw request bodies are represented by byte length and SHA-256 digest to minimize sensitive data.
- The versioned REST API exposes batch ingestion, device-scoped log collection/item
  reads, and the current authenticated identity. Auth0 remains the authorization
  server; the backend never issues local tokens.
- Agents upload gzip-compressed JSON batches: 1-500 records, at most 1 MiB compressed
  and 8 MiB expanded. Validation and JWT-bound device policy checks precede publishing.
- HTTP event storage retains request/response headers, captured source/destination
  IPs and ports, HTTP version, byte counts, duration, process name/PID and correlation
  ID, in addition to timestamp/method/URL/status. Only request bodies are hashed.
  Observed endpoints remain agent-reported and cannot overwrite the upload peer IP.
  Closed schemas reject unexpected/duplicate fields, coercible numeric types,
  invalid network values, unsafe header-map keys, controls and oversized fields
  before any publishing. See the README for precise limits and compatibility aliases.
  Stored text remains data, never an executable query or HTML.
- Logs use `traffic_logs`, a MongoDB time-series collection with `timestamp` as
  `timeField`, `metadata` as `metaField`, and `seconds` granularity. Metadata
  contains device identity and the server-owned Boolean `suspicious` classification;
  high-cardinality batch IDs must not fragment bucket metadata. The `ingestion`
  object contains server-owned `batch_id`, OAuth `client_id`, upload `source_ip`
  and `received_at`. `logdata` contains the captured HTTP fields, network/process
  observations and body content/length/digest. `_id` and event `timestamp` remain
  root fields, as does the optional `storage_encryption` envelope.
- Traffic records are indexed by device plus event time and record ID, and by
  `ingestion.received_at`. `(ingestion.batch_id, _id)` supports worker replay checks.
  Analysis pagination uses timestamp/ID keysets, not growing offsets; HTTP payload
  nesting does not require additional indexes for the current query API.
- Writes use primary with majority write concern. Analysis uses strict `SECONDARY`
  read preference with majority read concern; lack of a secondary is an explicit
  availability error, never a primary fallback. Single-node local development can
  explicitly select primary analysis; this option is rejected outside development.
  Replication lag is visible to deployment clients.
- A replica-set URI is mandatory, and direct connections are rejected.
- Ingestion attribution is server-owned. The verified JWT
  `https://amazing-http-logger/device_id` supplies device identity or
  defaults to `sub`. Verified `azp` (or `client_id`) supplies the optional OAuth
  client ID. Batch schemas forbid client attribution fields. Each upload has one
  authenticated device and enforces that device's primary-backed policy.
- Source IP comes only from the ASGI connection, after Uvicorn's explicitly
  trusted-proxy handling. Forwarding headers from untrusted peers and upload body
  fields cannot override it. Event timestamps and captured traffic remain
  agent-reported observations, distinct from server-generated ingestion metadata.
- Auth and authorization checks are mandatory for protected routes.
- Resources use globally unique device IDs, without user keys. Agents are limited
  to their JWT-bound device; `manage:devices` authorizes fleet-wide reads and
  management. Status acknowledgements always require the matching agent identity.
- The device-only identity schema uses an explicitly fresh test database.
  Traffic documents use nested `ingestion` and `logdata` fields.
  Startup never automatically resets data.

## Application encryption and management

- Workspace retention has independent enabled/window fields for ordinary logs
  (default 7 days) and suspicious logs (default 30 days); disabled means indefinite.
  Whole-day windows are bounded to 1-24855 by MongoDB's TTL seconds limit.
  Primary-backed versioned settings require `manage:devices` and apply to existing
  and future logs based on event time. On MongoDB 7+, two partial TTL indexes on
  `timestamp` filter `metadata.suspicious`; no collection-level TTL is permitted.
  Missing classifications are ordinary, and new ingestions always set false.
  Read APIs expose the flag, but agents cannot supply it. Analysis/classification
  jobs are out of scope: a future job must respect time-series metadata update
  restrictions and reclassify before ordinary expiration. A metadata update cannot
  target one measurement using its ID on MongoDB 7; per-record reclassification
  needs a separately designed supported rewrite/move workflow.
  Index changes are reconciled after settings CAS and at startup, with version
  rechecks for concurrent saves. MongoDB 7 requires rebuilding changed partial
  TTL indexes; DDL and settings are not atomic. Failed application returns 503,
  leaves the desired policy saved, and requires a retry/startup reconciliation.
  Expiration is asynchronous and bucket-based, not an exact deletion deadline.

- Application-wide workspace configuration exposes independent retention/encryption
  Booleans for request bodies, authorization headers and cookies. Both default to
  true. The **Storage and encryption** UI offers discard, retain encrypted
  (default), or retain plaintext. Discard takes precedence, removing header entries
  and body content before KMS/publishing, while preserving body byte length and
  SHA-256 digest metadata.
  Primary-backed versioned settings require `manage:devices`; omitted retention
  fields preserve existing choices. Changes affect future uploads only; existing
  logs are never migrated or rewritten.
- A separate non-exportable OpenBao Transit AES-256-GCM key encrypts selected
  fields before publishing, using randomized 96-bit nonces and record/device/batch
  associated data. Replica-backed detail reads decrypt retained bodies; collection
  reads omit bodies and credential values remain redacted. KMS failures fail closed.

- Non-local API traffic requires HTTPS through a trusted TLS gateway; forwarded
  schemes are accepted only from explicitly trusted proxy IPs/CIDRs.
- Per-device configuration lives in the regular `device_configurations`
  collection. Default version zero is `tls_only`; `optional` permits either upload
  format and `required` rejects plaintext. Policy reads use primary/majority for
  enforcement, independently of secondary-only analysis routing.
- `POST /api/v1/devices` atomically registers a named device and initial policy,
  guarded by `manage:devices` and global unique ID/name indexes. Registration time
  is server-generated. Existing IDs (including policy-only records) and names
  return `400` without overwriting state. Only policy edits accept expected versions.
  `GET /api/v1/devices` lists all accessible stored configuration records by
  device-ID keyset, including unnamed/version-zero agent and policy records;
  `GET /api/v1/devices/{id}` returns 404 only for absent records.
  The SSR registration form, inventory and dedicated `/devices/{id}` detail/policy pages use these
  primary-backed operational APIs; legacy unregistered-agent behavior is preserved.
- `GET /api/v1/devices/{id}/configuration` exposes policy and only the active public
  key. `PATCH` requires `manage:devices` and atomic expected-version matching.
  `PUT /api/v1/devices/{id}/configuration-status` records client capability and
  applied/unsupported/error status, with version and key checks.
- Application-encrypted uploads use JSON -> gzip -> compact JWE,
  a configured ECDH/AES suite (default NIST P-384, ECDH-ES+A256KW, A256GCM),
  `application/jose`, and authenticated protected key IDs and ephemeral public keys.
  Decryption precedes bounded decompression, validation, device policy checks,
  redaction, storage field encryption, and the publisher boundary. The original
  JWE does not cross that boundary; protected storage fields remain ciphertext.
- OpenBao Transit wraps the private EC key set using a non-exportable AES-256-GCM
  KEK; KV v2 stores only wrapped ciphertext with compare-and-swap. Runtime credentials
  grant only exact-record read and exact-key decrypt. EC keys are unwrapped into
  backend RAM at startup; JWE/ECDH decryption remains local because Transit does
  not provide ECDH JWE decryption. No plaintext EC files or private EC Secrets are used.
  One active public key is advertised; retained keys decrypt buffered batches.
  Staged rotation/activation and retirement require process restarts. KEK rotation
  rewraps ciphertext without changing client EC keys. JWE itself supplies no
  replay deduplication; request retry identity uses `X-Batch-Id`.
- Suite selection lives in environment/Helm configuration and drives key generation,
  client discovery, key validation, and decryption. Only NIST prime-field curves
  and supported ECDH/AES-KW/AES-GCM combinations are accepted. This is classical
  cryptography, not post-quantum protection or a FIPS validation claim.
- Clients must implement configuration polling and encryption support; changing
  backend policy cannot upgrade older agents. Roll out optional encryption first.
  Registration does not provision credentials or enroll Auth0 clients. Trusted
  issuer configuration must bind distinct devices to distinct device IDs.
- See [the encryption protocol](ENCRYPTION.md) for setup, limits, status semantics,
  proxy trust, OpenBao operations, and two-phase key rotation.

## Local development

- Docker Compose runs one MongoDB service as a self-initializing single-node replica
  set with a persistent volume and loopback port 28017. Its healthcheck waits for
  primary readiness; no extra initializer or secondary services are needed.
- Compose also runs one loopback-only, ephemeral OpenBao dev instance on port 28200.
  Bootstrap generates private ignored root/runtime credentials and provisions
  engines, wrapped keys, and least-privilege policy. KMS restarts lose keys; MongoDB
  storage persists. Production requires a separately operated persistent OpenBao.
- Compose also runs MinIO, a Pub/Sub emulator and a private object-event bridge.
  `make dev-up` provisions the bucket, notifications, topics and subscriptions.
- Development NGINX listens on 8080, routing API/docs to backend 9090 and other
  paths to frontend 3000, including Auth0 routes and HMR. Compose publishes the proxy
  port and uses the Docker Desktop host gateway by default. Native Linux uses a
  `proxy-host` service (`make dev PROXY_SERVICE=proxy-host`).
  Host applications remain loopback-only. All dependencies use one Compose file;
  profiles isolate development, spool, proxy variants and initialization tools.
- `make dev` waits for dependencies and runs the API with Uvicorn reload plus both
  parser and loader host processes. `make run` / `python -m app` run the API alone using `.env`;
  neither command builds an application image.
- Run `make spool-parser` and `make spool-loader` in separate terminals when
  starting components independently; workers do not share API auto-reload.
- Compose and Python share a parameterized `.env`, including URI interpolation,
  port 9090 for Python, frontend 3000 and proxy 8080, and a development-only primary-read flag.
- Kubernetes aligns backend 9090/frontend 3000 and uses an optional Ingress resource
  backed by an external Ingress controller rather than an additional proxy workload.
  MongoDB uses 27017, OpenBao 8200, and local API port-forward 9090.
  Deployment reads stay secondary-only.

## Kubernetes deployment

- `helm/amazing-http-logger` deploys the API as a non-root
  Deployment with resource limits, startup/liveness/readiness probes, no service
  general-purpose service-account token, and a read-only root filesystem. Its Service is ClusterIP.
  A dedicated ServiceAccount and audience-bound projected JWT authenticate to OpenBao.
- By default MongoDB is external and its URI comes from an existing Kubernetes
  Secret. Helm never renders database credentials or stores them in release values.
  Auth0's public tenant/audience settings are stored in a ConfigMap.
- Two separately scalable worker Deployments always use the same application image
  and `python -m app.spool_worker parse/load`. The parser has upload decryption and
  field-protection credentials; the loader needs Mongo and scoped storage/Pub/Sub
  permissions but no EC/KMS credentials. Both use hardened non-root/read-only settings.
  Keep termination grace and stage leases longer than in-flight processing plus
  network/acknowledgement/cleanup margins.
- Production defaults to external HTTPS OpenBao with preconfigured Kubernetes auth;
  optional credential/CA Secrets are mounted read-only. No private EC key Secrets
  or production KMS initialization/unsealing are installed by this chart.
- `values-development.yaml` opts into an unauthenticated three-member MongoDB
  StatefulSet with per-member PVCs, stable headless-Service DNS, and an ingress
  NetworkPolicy. It is not a production database deployment.
- The development profile also bundles ephemeral OpenBao, a generated root Secret,
  TokenReview RBAC, and an idempotent bootstrap Job. Only server/bootstrap pods
  mount the root credential; API pods receive least-privilege Kubernetes login.
  Bundled KMS restarts require bootstrap/API/parser rollout and cannot recover lost keys.
- MongoDB's ingress policy includes both workers. An enforcing NetworkPolicy CNI is required.
- All MongoDB pods start in parallel. The headless Service publishes not-ready
  addresses, allowing initialization before replica-role readiness succeeds.
  A normal, revision-named Job initializes or validates the replica set; it is not
  a post-install hook, which would deadlock Helm's readiness wait.
- API init containers wait for primary connectivity and KMS provisioning. Application lifespan
  still validates time-series storage before the HTTP server starts. Probes are
  process-health checks; loss of a secondary does not prevent primary ingestion.
- Helm deployments rerun the idempotent initialization check. PVCs remain after
  uninstall; use a stable release name and namespace for the development database.

## Transport and receipt boundaries

`POST /api/v1/traffic-log-uploads` returns `202` only after durable raw storage.
Optional device-scoped `X-Batch-Id` returns `200` for identical-byte/format retries
and `409` for conflicting content. `GET` on the upload ID exposes validation,
persistence and cleanup status. Malformed content fails asynchronously.

Object-event Pub/Sub triggers `app.spool_worker parse`. It decrypts, bounds
decompression, validates, normalizes and applies the acceptance-time policy
snapshot. Silver carries gzip BSON capped at 9,500,000 wire bytes and 32 MiB
expanded. Oversized protected output fails parsing without deleting raw.

`app.spool_worker load` waits for per-replica rate capacity before pulling, uses
atomic receipt leases, and writes Mongo with majority acknowledgement. Only a
majority `stored` receipt permits raw deletion. Cleanup retries never reload
stored records. Both workers default to three application attempts; Terraform
configures native Pub/Sub redrive at five and retention at 14 days. Application
dead letters are sanitized pointers; native load redrive can include protected
normalized documents. Restrict both DLQs and retain their inspection subscriptions.

Pending/failed raw data has no age TTL, versioning or soft deletion. Operators
use targeted replay/cleanup after repairing dependencies; message expiration
does not delete raw. Delivery remains at least once: deterministic IDs and
missing-ID checks cannot prevent every ambiguous time-series write duplicate.
