# Amazing HTTP Logger

Python backend for collecting and persisting HTTP traffic logs generated by software agents running on user devices.

## Overview

The application is responsible for:

- authenticating users and agents
- accepting traffic log payloads from installed agents
- validating and normalizing incoming HTTP metadata
- persisting the data to MongoDB
- exposing a secure API for later analysis and investigation

## Stack

- Python 3.11+
- FastAPI
- Pydantic
- MongoDB with native async PyMongo
- Auth0FastAPI SDK for access-token verification and cached discovery/JWKS
- HTTPX2 for HTTP clients and API tests
- OpenBao Transit and KV v2 for key management
- Next.js SSR management console in `frontend/` (JavaScript/JSX, shadcn/ui)
- pytest
- GCS raw upload spool and two Pub/Sub stages; real MinIO and Pub/Sub emulator locally
- Separate parser/protect and rate-limited Mongo loader workers
- Docker Compose for development dependencies; Terraform/Cloud Run on GCP, optional Kubernetes/Helm
- ruff or flake8

## Core ingestion flow

All ingestion uses durable raw uploads, object events and two independent workers.
Identity, device policies, workspace retention, analysis reads and the frontend
use their existing APIs.

```text
POST /api/v1/traffic-log-uploads
  -> authenticate / device policy / wire-size limit / policy snapshot
  -> immutable raw object in GCS (MinIO in local development)
  -> HTTP 202 {upload_id, status: "received", duplicate: false}
              |
       GCS OBJECT_FINALIZE -> Pub/Sub pull subscription
       Local: MinIO ObjectCreated -> private webhook bridge -> Pub/Sub emulator
              |
  worker #1: JWE decrypt -> bounded gzip / JSON validation -> normalize
             -> snapshot discard rules / existing field encryption
              |                                \-> parse DLQ
       separate Pub/Sub silver topic / pull subscription (protected documents)
              |
  worker #2: per-upload lease / replay checks -> rate-limited unordered Mongo writes
              |                                \-> load DLQ
       mark upload stored -> delete raw object -> Pub/Sub ACK
```

**The raw object is a temporary durable spool, not a historical datalake.** The
collector does not decompress, decrypt, count records or call field-encryption
Transit for this endpoint. It still reads the device/workspace policies, hashes
the bounded wire bytes, reserves a small Mongo receipt and waits for a successful
object write. This reduces request-path processing, not necessarily total work.
GCS upload latency and receipt writes must be included in latency measurements.

### Contract and policy boundaries

The upload accepts gzip JSON (1 MiB compressed / 8 MiB expanded / 1-500 events), or compact
JWE (1,500,000 wire bytes). Only format, wire size, authentication, trusted
attribution and device transfer policy are checked before acknowledgement.
Bad JWE, gzip, JSON or records fail **asynchronously**, without partially loading
the batch. Therefore the POST receipt has **no `accepted_count`**.

Poll `GET /api/v1/traffic-log-uploads/{upload_id}` for `status`, nullable
`accepted_count`, sanitized `error_code`, and `raw_deleted`. States are
`uploading -> received -> parsing -> queued -> loading -> stored`, with
`parse_failed` / `load_failed` for dead-lettered uploads. A fast worker may
advance the receipt before POST returns. `stored` confirms majority Mongo
persistence; `raw_deleted=true` also confirms cleanup. Agents can inspect only
their device's uploads; `manage:devices` permits fleet status reads. These are
operational primary reads, not primary-backed analysis queries.

**Raw-retention privacy boundary:** original upload bytes are
temporarily stored, including fields configured to be discarded later. GCS uses
encryption at rest, public-access prevention and scoped workload IAM. Gzip-only
uploads are not application-encrypted. The local MinIO volume is development-only
and does **not** promise production encryption at rest; use synthetic data.
Worker #1 applies the workspace storage-policy **snapshot taken at acceptance**,
so policy edits during a backlog do not change already accepted uploads.
Authentication tokens are never saved with objects. Device identity/source IP
come from the collector, never from uploaded log fields.

### Medallion mapping and delivery guarantees

| Stage | Tier | Responsibility |
| --- | --- | --- |
| Collector | Ingress | Authenticate, cheap validation, reserve receipt, persist raw bytes before acknowledging |
| GCS / local MinIO | Temporary bronze | Immutable replay source until Mongo persistence |
| Worker #1 (`app.spool_worker parse`) | Bronze to silver | Decrypt, decompress, validate, normalize, minimize and encrypt fields |
| Separate Pub/Sub topic/subscription | Silver transport | Managed buffering, delivery leases, redelivery, explicit ACK and load DLQ |
| Worker #2 (`app.spool_worker load`) | Silver to gold | Rate-limited Mongo loading and post-persistence cleanup |
| MongoDB `traffic_logs` | Gold | Existing hot analysis store and workspace-controlled TTL |

Workers are separately deployable/scalable: worker #1 contains CPU-heavy parsing
and all ingestion cryptography/KMS access; worker #2 isolates Mongo I/O and needs
no upload keys or field-encryption credential. No new enrichment/classification
or query functionality is introduced.

Optional `X-Batch-Id` (1-128 ASCII letters/digits/`._:-`) makes identical-byte
retries idempotent per authenticated device. A duplicate returns HTTP **200**
with `duplicate=true`; different bytes or format under the same ID return **409**.
Without the header, each request is a new upload. Receipts are retained without
TTL so completed keys do not silently become reusable.

The raw object uses a conditional create (`if_generation_match=0`; MinIO
`If-None-Match: *`) and a partitioned key:
`raw/tenantId=<deployment-hash>/date=<YYYY-MM-DD>/agentId=<device-hash>/<upload_id>.upload`.
`SPOOL_TENANT` is a deployment namespace, **not** a new authentication tenant.
A versioned JSON header, newline and original wire bytes form one atomic object;
the header contains the trusted context, policy, checksum and receipt ID.
Operational state in `ingestion_uploads` enforces unique object keys, atomic
per-stage claims, expiring leases, bounded attempts and terminal duplicate skips.
Stable event identities are `<upload_id>:<index>` and derive deterministic Mongo
record IDs. Partial/replayed writes reuse the existing majority-read missing-ID
check and `insert_many(..., ordered=False)`.

Delivery remains **at least once, not exactly once**: Mongo time-series cannot
enforce unique measurement IDs or transact the receipt with measurement inserts.
Leases prevent ordinary competing writes; a network-ambiguous in-flight insert
can still duplicate records. The implementation does not claim otherwise.

### Backpressure, cleanup and recovery

The pipeline uses **Pub/Sub for both hops**, with separate object-event and
silver subscriptions.
Pub/Sub stores backlog outside worker memory; pull consumers fetch one message
at a time, explicitly ACK completed work, and use delivery-deadline expiry to
recover crashed consumers. Transient loader failures release the delivery for retry.
The loader waits for rate capacity **before pulling**, avoiding expired leases
while throttled. GCP subscriptions default to **14-day retention**, configurable
with `spool_message_retention_seconds`; expiration requires replay from raw rather
than silently deleting the upload. There is no in-memory MAXLEN trimming.

Silver messages contain normalized, field-protected BSON with gzip **transport**
compression; worker #2 never decrypts or reparses original uploads. Compression
also accommodates encrypted-field expansion beneath Pub/Sub's 10 MB request
limit. Encoding and bounded decoding enforce 9,500,000 wire bytes and 32 MiB
expanded; exceptional oversized output is explicitly parse-dead-lettered with
`silver_payload_too_large`, retaining the original raw object.

Worker #2 permits `SPOOL_MONGO_DOCUMENTS_PER_SECOND` **per replica**, with an
initial burst of at most one batch (500 documents). Multiply by loader replicas
for deployment capacity. Both workers default to three application attempts,
then publish a sanitized pointer to the corresponding Pub/Sub DLQ before ACK.
Both GCP subscriptions also use native DLQ redrive after five delivery attempts,
the platform minimum, and exponential retry backoff.
DLQ publication failure leaves the work unacknowledged.
Application dead letters contain sanitized pointers. Native Pub/Sub redrive
forwards the original message, so the load DLQ can contain protected normalized
documents (including fields intentionally retained as plaintext by policy).
Restrict inspection access and never dump message bodies into logs or tickets.

Raw deletion happens only **after** Mongo success and a majority `stored` receipt.
Cleanup failures retry deletion without repeating Mongo writes. Objects recreated
by an ambiguous late collector PUT also trigger cleanup-only work, without
reloading Mongo. Pending/failed
objects have **no automatic age TTL**: they remain until successful processing or
an explicitly approved operator deletion. GCS versioning and soft deletion are
disabled on this dedicated bucket so consumption does not retain hidden raw
copies. Do not add lifecycle expiration, backups or replication that contradict
this temporary-data policy without reviewing replay and privacy requirements.

Recovery: fix the parser/KMS/Mongo issue, replay the specific receipt with
`python -m app.spool_worker replay <upload_id>`, verify `stored` and
`raw_deleted=true`, then acknowledge its inspected DLQ message. For a stored
receipt whose cleanup entry was lost, use
`python -m app.spool_worker cleanup <upload_id>`. Never replay an active lease or
delete a raw object merely because worker #1 published it. See the
[runbook](docs/RUNBOOK.md#upload-ingestion) for setup and operational details.

Metrics are emitted as `metric=<name> value=<number>` log records:
`ingest.batch.accepted`, `ingest.batch.duplicate`, `ingest.parse.success`,
`ingest.parse.dlq`, `ingest.load.success`, `ingest.load.dlq`,
`mongo.write.latency_ms`, `pipeline.e2e.latency_ms`.
Pub/Sub's `subscription/num_undelivered_messages` and
`subscription/oldest_unacked_message_age` supply managed backlog metrics.
GCP Terraform provisions DLQ-depth and silver-backlog depth/age alerts using
`notification_channels`; defaults warn above 500 messages or one hour of age.
Helm operators must configure equivalent cloud alerts for their subscriptions.
Do not treat local emulator metrics as production latency evidence.

Expected end-to-end latency is driven by object-event delivery, Pub/Sub polling,
parsing/KMS, Pub/Sub backlog and Mongo write capacity; **p50 2-10 seconds is a target,
not a measured guarantee**. The object upload itself can make acknowledgement
slower for small batches. Benchmark upload acknowledgement and observed persistence
with the runbook tool. Monitor Pub/Sub quotas, backlog
age, cost and Mongo drain capacity as volume grows. GCS remains the temporary
replay source; this implementation intentionally adds **no cold historical tier**.

### Shared public origin

NGINX is the open-source development reverse proxy. It routes `/api/v1`, `/docs`,
`/redoc`, `/openapi.json` and `/health` to Python **9090**; all other paths, including
`/auth/*`, dashboard pages and Next.js assets/HMR, go to Next.js **3000**. Paths and
gzip/JWE request bodies are preserved. `/proxy-health` checks NGINX itself.
The upstream response-header buffer is 16 KiB to accommodate Auth0/Next.js
cookie headers; the default NGINX buffer can otherwise return 502 on sign-in.
For the community NGINX Ingress controller, set
`nginx.ingress.kubernetes.io/proxy-buffer-size: "16k"` under `ingress.annotations`
for the same header allowance.

Compose publishes proxy port **8080** to host loopback by default. Docker Desktop
uses `host.docker.internal` to reach the host-run backend and frontend; no override
or host-networking setting is needed. On native Linux, use host networking to
reach applications bound to loopback. For example:

```bash
make proxy-up PROXY_SERVICE=proxy-host
```

Use `make dev PROXY_SERVICE=proxy-host` for the complete native-Linux workflow.
`proxy-up` stops the other proxy variant when switching modes; `proxy-down`
stops either variant. Shutdown does not require repeating the selector.

The proxy defaults to loopback **8080**. Point a local domain or an HTTPS tunnel at
that listener, not separately at the frontend/backend. To use a trusted HTTPS tunnel,
set `PROXY_EXTERNAL_SCHEME=https`; keep the proxy loopback-only so arbitrary clients
cannot bypass TLS termination. NGINX replaces, rather than trusts, client-supplied
forwarding headers. Host applications trust only the actual local proxy peer.

Set frontend `APP_BASE_URL` to the public proxy origin (locally
`http://localhost:8080`) and register its `/auth/callback` and logout origin with
Auth0. Keep `BACKEND_API_URL=http://127.0.0.1:9090` for host-run SSR API calls.
This setting must be an origin without an `/api` or `/api/v1` suffix: frontend
request paths already include `/api/v1`, and the proxy preserves that prefix.
Existing `.env` files override new defaults: migrate `APP_PORT` to **9090**, keep
`FRONTEND_PORT=3000`, and restart applications and the proxy after changing settings.

### 6) REST API

All `/api/v1` endpoints require an Auth0 access token in `Authorization: Bearer <token>`.
Clients authenticate with Auth0 directly (Authorization Code with PKCE for user-device
agents); this API does not issue tokens or proxy the IdP's authorization/token endpoints.
`GET /api/v1/me` verifies the resulting identity. Interactive OpenAPI docs are at `/docs`.
Each operation includes a brief description and an explicit **Required permission**
section, including own-device restrictions and where `manage:devices` grants fleet access.
Request and successful response schemas include examples. The batch JSON example is
shown before compression: Swagger UI does not gzip or encrypt it; use an HTTP client
to send gzip bytes or a real compact JWE.
Tokens must use RS256 and include `exp`, `iat`, `iss`, `aud`, and a nonempty `sub`.
Verification uses `Auth0FastAPI.require_auth()` and the configured tenant's HTTPS
discovery/JWKS. Proof-bound tokens are not supported by this Bearer-only API.
SDK validation failures return sanitized `401` responses; unexpected SDK failures
return `503`. The SDK currently imports deprecated `authlib.jose` internally; this
upstream warning remains visible. Application JWE encryption uses `joserfc`.

#### Register a device and configure its policy

Open **Device policies** in the frontend, enter the device's exact JWT-bound ID
and a display name, choose **TLS only**, **Optional JWE**, or **Required JWE**, and
select **Register device**. The authenticated Server Action calls the backend;
the device appears in the API-backed **Devices** list. The list also includes
existing records created by agent acknowledgements or policy changes, even without
a name or registration timestamp. Select a device to open its dedicated details
page, inspect the policy/public key, save later policy changes, see the agent's
versioned acknowledgement, or navigate to its traffic. Both registration and policy writes require
`manage:devices`; listing and viewing your own devices do not.

The equivalent API request is:

```http
POST /api/v1/devices
Content-Type: application/json
Authorization: Bearer <operator-access-token>

{"device_id":"issuer-bound-device","name":"Operator laptop","encryption_mode":"optional"}
```

Registration stores `name`, server-generated `registered_at`, and the initial
policy in **one primary/majority atomic insert**, returning `201`, a resource
`Location`, and configuration version 1. Device IDs and names are globally unique
(case-sensitive, exact matching after frontend whitespace trimming).
An existing ID or name returns **`400 Bad Request`**, including concurrent
registrations, without changing the existing device or policy. JWE modes require available public encryption keys before
any write. Names are 1–128 characters; IDs are 1–255 characters and a single URL
path segment. Blank/control-containing text and unexpected fields are rejected.

An existing policy/status record also reserves its device ID: registration returns
`400`, rather than adopting or overwriting it. Use the policy editor to change an
existing policy; only policy PATCH uses `expected_version` and returns `409` on
concurrent edits. Registration does not accept `expected_version`.
Existing unregistered agents and version-zero policy lookups remain supported;
registration is inventory, not a new ingestion gate.

`GET /api/v1/devices?limit=25` returns `{items, next_after}` sorted by device ID.
Pass `next_after` unchanged as `after` for the next page (`limit` 1–100).
All persisted device configuration records appear, including version-zero agent
records. `name` and `registered_at` are nullable when not explicitly registered;
the UI labels these records rather than inventing registration metadata.
`GET /api/v1/devices/{id}` returns `404` only when no stored record exists.
Looking up an unknown ID through `/configuration` still returns its effective
TLS-only default, but does not create an inventory entry. All inventory/policy
operations use the primary, while traffic analysis keeps its replica routing.
A stored record is not proof that an agent is online.

**Identity boundary:** resources are identified only by globally unique `device_id`,
not by a user/device pair. Operators with `manage:devices` can manage the fleet;
ordinary agents can read only their own device's inventory, policy and logs.
Explicit queries for another device return `403`; another device's log ID returns
`404`. Status reports must match the JWT-bound device, even for management tokens.
Use the ID returned by the agent's `/api/v1/me`; arbitrary registration IDs do not
change JWT identity. This workflow does **not** create Auth0 clients or credentials.
Grant management access only to trusted operators: it is global, not tenant-scoped.
This test application uses a fresh database for the device-only schema; old test
data is discarded, not migrated.

#### Upload a batch

Send `Content-Type: application/json` and `Content-Encoding: gzip`. The decompressed
body is `{"logs": [...]}`, containing 1-500 traffic records.
Attribution is server-owned: do not send `user_id`, `device_id`, `client_id`,
`source_ip`, `metadata`, record/batch IDs or ingestion timestamps in a record.
Such extra fields fail asynchronous content validation.
A batch is limited to 1 MiB
compressed and 8 MiB decompressed; malformed/truncated gzip, trailing data, and
concatenated gzip members are rejected.

Each stored record retains the HTTP event, **not just a hash**: timestamp, method,
URL, status, request/response headers, optional network endpoints,
sizes, duration and process context. Original bodies and captured authorization/cookie
values are retained under the workspace's storage policy, encrypted by default.
Body UTF-8 byte length and SHA-256 are also retained for correlation.
Authorization/cookies remain redacted in API responses; collection reads omit bodies,
while authorized request details can decrypt and display retained bodies.

An expanded agent record looks like this (all fields after `status_code` are optional):

```json
{
  "timestamp": "2025-01-15T10:23:45.123Z",
  "method": "POST",
  "url": "https://api.example.com/v1/login",
  "status_code": 200,
  "request_headers": {"User-Agent": "Mozilla/5.0", "Content-Type": "application/json"},
  "response_headers": {"Content-Type": "application/json"},
  "captured_source_ip": "192.0.2.10",
  "destination_ip": "203.0.113.50",
  "source_port": 49152,
  "destination_port": 443,
  "http_version": "2",
  "request_size_bytes": 256,
  "response_size_bytes": 1024,
  "duration_ms": 12.5,
  "process_name": "chrome.exe",
  "process_id": 1234,
  "request_id": "agent-request-123"
}
```

`source_ip` in the **stored/read** record remains the trusted upload peer. Use
`captured_source_ip` for the observed request's origin; an agent cannot overwrite
ingestion attribution. Destination addresses are validated literals, not resolved
through DNS or independently verified by the backend. Optional observations absent
from an older record return `null` (header maps return `{}`).
`headers` is accepted as a legacy input alias for `request_headers`, but supplying
both is rejected. New storage uses `logdata.request_headers`; API reads also return the
deprecated `headers` alias and support historical documents without migration.

#### Strict event validation

Both gzip and decrypted JWE batches use the same closed schema. Any invalid
record rejects the **entire batch asynchronously before silver publishing**.
Wire-size violations return `413` synchronously; expanded-size violations fail
asynchronously. Status errors do not echo captured values.

| Fields | Validation |
| --- | --- |
| Batch and records | No unexpected fields or duplicate JSON keys; UTF-8 JSON; 1–500 records; existing 1 MiB gzip/8 MiB expanded limits |
| `timestamp` | ISO 8601 with seconds and timezone, normalized to UTC; epoch numbers/strings rejected |
| `method`, `url`, `status_code` | HTTP token up to 16 characters, normalized uppercase; HTTP(S) URL up to 8192 characters without credentials, raw controls or surrounding whitespace; integer 100–599 |
| Both header maps | At most 100 entries and 32 KiB combined UTF-8 key/value bytes per map; names ≤256 characters, values ≤8192; no controls or case-insensitive duplicates |
| Header keys | HTTP tokens; dots, dollar signs and prototype-map keys are rejected, not interpreted as paths/operators |
| Captured IPs and ports | IPv4/IPv6 literals without zone IDs; integer ports 1–65535 |
| HTTP version | `1.0`, `1.1`, `2` or `3` |
| Message sizes | Agent-measured request/response byte counts, integers 0 through signed BSON int64 maximum; no numeric-string/boolean coercion |
| `duration_ms` | Finite nonnegative milliseconds, at most 24 hours; no numeric strings, NaN or infinity |
| Process context and correlation | Nonblank, control-free process name ≤255 characters; integer PID 0–2147483647; request ID ≤128 ASCII letters/digits/`._:-`, starting alphanumeric |
| Optional `body` | String up to 1,000,000 characters; valid UTF-8; storage encryption enabled by default |

Captured text is **untrusted data**, even after validation. Valid URLs/header values
may contain attack attempts worth analyzing: validation is not a SQL/HTML sanitizer.
Queries use fixed server-owned field/operator names and typed values, never
`$where`, eval, string-built queries or uploaded query expressions. The dashboard
renders values as escaped text, never raw HTML. Any future analytics/export consumer
must preserve this separation and use output-context escaping/parameterized queries.

```bash
printf '%s' '{"logs":[{"timestamp":"2026-10-24T05:00:00Z","method":"GET","url":"https://example.com/","status_code":200}]}' |
  gzip -c |
  curl -X POST http://localhost:8080/api/v1/traffic-log-uploads \
    -H "Authorization: Bearer $ACCESS_TOKEN" \
    -H "Content-Type: application/json" \
    -H "Content-Encoding: gzip" \
    --data-binary @-
```

The HTTP `202` receipt contains `upload_id`, `status=received`, and `duplicate=false`,
confirming durable raw storage, not validated records or Mongo log persistence.
Poll the upload status endpoint for asynchronous errors, `stored` and `raw_deleted`.
With optional device-scoped `X-Batch-Id`, identical bytes/format return `200`
with `duplicate=true`; conflicting reuse returns `409`. Without it each request
creates a new upload. Delivery remains at least once: partial or ambiguously
acknowledged Mongo time-series writes can still duplicate records.

#### Trusted ingestion attribution

- No user identity is persisted or exposed as a resource key.
- `device_id` is the verified `https://amazing-http-logger/device_id` claim when
  present, otherwise `sub`. A missing claim therefore means one logical device
  per principal; separate physical devices need issuer-managed, device-bound
  credentials/claims. Invalid identity claims return `401`, not a fallback.
  Configure the namespaced claim through trusted issuer-side data, never editable
  user metadata or values copied from a token request.
- OAuth `client_id` comes from verified `azp`, or `client_id` when `azp` is absent.
  It is `null` if neither claim exists; the backend never stores the JWT itself.
- `source_ip` is the upload connection address supplied by ASGI, including
  Uvicorn's trusted-proxy resolution. Payloads and arbitrary forwarding headers
  cannot set it. Configure `FORWARDED_ALLOW_IPS` only for actual gateways, restrict
  direct backend access, and ensure gateways sanitize forwarded addresses.
  Without a network peer the value is `null`; no IP is invented.
- IDs and `received_at` are server-generated. Event `timestamp`, URL, method,
  status, headers, captured endpoints, sizes/timing, process context and body
  remain **agent-reported traffic observations**, not
  independently verified facts. The upload IP is not the source of each captured
  HTTP request and may identify a NAT or proxy, not a physical device.

Call `/api/v1/me` first and use its `device_id` to poll configuration and report
status. Each batch belongs to this single JWT-bound device; its policy is read
from primary before publishing. Existing policies under client-chosen IDs must be
recreated for the JWT-bound ID, or the issuer must bind that existing ID in the
signed device claim. Source IP/device provenance is not retroactively verified,
and missing OAuth
client IDs are returned as `null`.

#### Encryption and remote client configuration

HTTPS is required outside local development; gzip alone is not encryption.
Devices default to `tls_only`. Administrators can set `optional` or `required`
application encryption, and clients poll their effective configuration every 300
seconds. Required encryption rejects plaintext batches regardless of client claims.
Clients must implement polling and JWE support; the backend cannot upgrade old agents.

Encrypted uploads use JSON -> gzip -> JWE compact serialization with
the server-configured curve and algorithms (default: NIST `P-384`,
`ECDH-ES+A256KW`, and `A256GCM`). Select them with `ENCRYPTION_CURVE`,
`ENCRYPTION_KEY_ALGORITHM`, and `ENCRYPTION_CONTENT_ALGORITHM`, or their Helm
`encryption` values. The API advertises the selected suite and only public keys.
OpenBao Transit wraps the private EC key set under a non-exportable KEK; KV v2
stores only its ciphertext. The backend unwraps the set into RAM at startup,
then performs JWE decryption locally: this is not remote ECDH or non-exportable EC keys.
No plaintext EC key files or private EC key Secrets are used. Parser workers decrypt,
minimize and protect fields before silver publishing. Management/enforcement
reads use primary to avoid stale policies; analysis remains secondary-only.

See [encryption setup and client protocol](docs/ENCRYPTION.md) for KMS provisioning,
management requests, encrypted uploads, HTTPS proxy settings, and key rotation.

#### Analyze logs

`GET /api/v1/traffic-logs` supports `device_id`, timezone-aware `start_time` (inclusive),
`end_time` (exclusive), `limit` (1-100, default 50), and an opaque `cursor`. Results are
ordered by event timestamp and record ID, descending. Pass `next_cursor` unchanged,
with the same filters, to retrieve the next page; `null` marks the end. Concurrent or
late-arriving events do not provide a snapshot across pages.

Agent analysis queries are restricted to the JWT-bound device. Management tokens
can read the fleet or select a device. Deployments use strict `SECONDARY` routing
with majority read concern and never fall back to primary: no secondary means `503`.
The single-node local profile explicitly selects primary reads instead.
Replica reads are eventually consistent, so a just-ingested record may temporarily
be absent (including `404` on a single-record lookup).

#### Storage and ingestion boundary

Logs use the `traffic_logs` MongoDB time-series collection, with `timestamp` as the
time field and `{device_id, suspicious}` as bucket `metadata`. Startup validates the
collection options and creates query indexes. Writes use the elected primary with
majority acknowledgement. `MONGO_URI` must specify `replicaSet`; `directConnection=true`
is rejected so analysis cannot accidentally read a standalone or primary.

#### Stored document layout

New MongoDB records separate bucket identity, trusted collector provenance and
agent-reported HTTP observations:

```javascript
{
  _id: ObjectId("6add2bcd3a25072164dd8cc9"),
  timestamp: ISODate("2026-10-24T22:06:05.206Z"),
  metadata: {
    device_id: "example-device",
    suspicious: false
  },
  ingestion: {
    batch_id: "4d737a07-51a6-4164-abb3-6ea75350b6fd",
    client_id: "example-oauth-client",
    source_ip: "127.0.0.1",
    received_at: ISODate("2026-10-24T22:06:05.211Z")
  },
  logdata: {
    method: "GET",
    url: "https://example.test/",
    status_code: 200,
    request_headers: {},
    response_headers: {},
    captured_source_ip: null,
    destination_ip: "203.0.113.50",
    http_version: "2",
    response_size_bytes: 1024,
    duration_ms: 12.5,
    process_name: "example-agent",
    body_length: 0,
    body_sha256: null
  }
}
```

The example omits other optional observation fields. A retained plaintext body
lives at `logdata.body`; encrypted values instead live in the root
`storage_encryption` envelope, with `[ENCRYPTED]` header placeholders in `logdata`.
Discarding the body still preserves `logdata.body_length` and `logdata.body_sha256`.

`metadata` is MongoDB's **bucket grouping key**, not a general-purpose metadata
bag. Batch IDs, reception timestamps and upload IPs vary per upload; putting them
there would fragment buckets and reduce compression. They belong in `ingestion`.
Event `timestamp` stays at the root because it is the time-series `timeField`;
`suspicious` stays in `metadata` for the two partial TTL indexes.

Query indexes cover `(metadata.device_id, timestamp, _id)`, `(timestamp, _id)`,
`ingestion.received_at`, and `(ingestion.batch_id, _id)` for worker replay checks.
No unused HTTP-field indexes are added.
The [runbook](docs/RUNBOOK.md#storage-initialization) describes storage initialization.
Agent upload events and traffic-log read responses are flat; direct database
consumers use the nested storage paths. The frontend consumes analysis responses,
not raw or silver objects.

Selected sensitive fields are encrypted before silver publishing,
using a dedicated, non-exportable OpenBao storage key, not the upload key set or its
wrapping key. With encryption enabled, neither the publisher nor MongoDB receives
the selected plaintext. Discarded categories are removed before this boundary;
explicitly disabling encryption for a retained category permits plaintext storage.
`X-Api-Key` remains discarded/redacted. Silver Pub/Sub hands batches to
`python -m app.spool_worker load`, which inserts them with majority acknowledgement.
See [the plan](docs/PLAN.md) for the producer/worker contract.

#### Durable ingestion

The [core flow](#core-ingestion-flow) defines the sole upload pipeline.
HTTP acknowledgement confirms raw durability; parser validation and protection
precede silver publication, and only the rate-limited loader writes traffic logs.
There is no synchronous Mongo log-write fallback. Monitor both subscriptions,
both DLQs, receipt state and raw cleanup independently of analysis replica lag.

#### Workspace storage and encryption

Open **Workspace > Storage and encryption** (`/settings`) to choose **Do not retain**,
**Retain encrypted** (the default), or **Retain plaintext** independently for request
bodies, authorization headers, and cookies for **all devices**. Discarded bodies
are not stored or encrypted, but their byte length and SHA-256 digest are retained.
Discarded authorization/cookie header entries are removed from both
captured header maps before publishing. Choices apply to **future uploads**;
existing logs are never rewritten or migrated. Discarded data cannot be recovered.

`GET/PATCH /api/v1/workspace/configuration` require `manage:devices`; PATCH requires
the three `encrypt_*` Boolean fields and `expected_version`. Three independent,
strict Boolean `retain_request_body`, `retain_authorization_header`, and
`retain_cookies` fields default to true and are preserved when omitted in PATCH.
`retain_*=false` takes precedence over encryption; retained fields use encryption
unless deliberately configured otherwise. Concurrent edits return
`409`; configuration writes and enforcement reads use primary/majority, while log
analysis still reads replicas. Saving validates KMS availability only for categories
configured to retain encrypted values; ingestion never sends discarded values to KMS.

The dedicated `OPENBAO_STORAGE_KEY` (default `log-storage`, Helm `openbao.storageKey`)
is generated and retained inside OpenBao Transit as non-exportable
`aes256-gcm96`: AES-256-GCM with randomized 96-bit nonces and authenticated
record/device/batch binding. It is distinct from `OPENBAO_TRANSIT_KEY`.
Bootstrap/`python -m app.kms initialize` provision it without replacing existing
keys. `python -m app.kms rotate-storage` creates a new version while old versions
remain available for old records. New keys auto-rotate every 30 days; operators
must also rotate before per-version usage limits are reached. Missing keys or KMS
failures prevent encrypted operations: workspace/read failures return `503`,
while parser KMS failures are asynchronous and retain raw for retry/recovery.
There is never a plaintext fallback or fabricated stored status.
See [storage standards and key retention](docs/ENCRYPTION.md#workspace-storage-encryption)
before using persistent logs.

#### Retention policies

The **Workspace** page has independent, enabled-by-default retention windows:
**7 days for ordinary logs** and **30 days for suspicious logs**. Either can be
disabled to retain that category indefinitely. Windows are whole days, 1-24855.
They apply to all devices and existing records, measured from the captured event
`timestamp`, not upload time or classification time. Shortening/enabling retention
can permanently delete old data; increasing/disabling it cannot restore deleted logs.

Workspace GET/PATCH expose `retention_enabled`, `retention_days`,
`suspicious_retention_enabled`, and `suspicious_retention_days`, under the same
`manage:devices` permission and `expected_version` concurrency check as encryption.
The UI saves both sections together. Existing API clients can omit retention
fields when updating encryption; omitted values are preserved.

MongoDB **7.0+** uses separate partial TTL indexes on `timestamp`, filtered by
`metadata.suspicious`. There is no collection-wide TTL that could delete
suspicious logs under the ordinary window. New logs get a server-owned
`metadata.suspicious: false`; historical logs without it count as ordinary.
Collection/item analysis responses expose `suspicious`. Agents cannot set it;
the analysis job and classification writes are **not implemented**. A future job
must handle MongoDB's time-series update restrictions when reclassifying records
and classify them before ordinary expiration; expired evidence cannot be recovered.

Expiration runs asynchronously on whole time-series buckets, so deletion may lag
the window by a bucket span (normally up to one hour) plus TTL-monitor/load delay.
Saving settings reconciles the indexes; startup reapplies the saved policy.
MongoDB 7 requires dropping/rebuilding the affected partial TTL index to change
its window. Settings and index DDL are not transactional: on failure the API returns
`503`, but settings may already be saved. Reload and retry after fixing database
permissions/connectivity, or restart to reconcile; never assume a failed save
disabled expiration. See the [retention runbook](docs/RUNBOOK.md#retention-operations).

Helm remains the deployment path. Its development profile includes a three-member
MongoDB StatefulSet, independently scalable parser and loader Deployments,
ephemeral OpenBao with Kubernetes-auth bootstrap, frontend on **3000**, API on **9090**,
and placeholder Auth0 settings. Set `frontend.appBaseUrl` to your public HTTPS origin
and `frontend.auth0.existingSecret` to the existing frontend Auth0 Secret.
Development spool resource names are illustrative linting values, not bundled
cloud resources. Override them with real GCS/Pub/Sub resources and workload
identity before deployment; Docker, not Helm, supplies local MinIO/emulators.
The frontend calls the HTTPS public origin for SSR unless `frontend.backendApiUrl`
provides another HTTPS endpoint. Both browsers and frontend pods must resolve and
reach that endpoint.

Enable `ingress.enabled` and configure its host, class and TLS Secret as documented
in the [runbook](docs/RUNBOOK.md). An installed **Ingress controller** performs
reverse proxying and TLS termination; the chart creates routing configuration,
not a redundant proxy Deployment or an Ingress controller. Configure Auth0 callback
`https://YOUR_HOST/auth/callback` and the matching logout origin. When enforcing HTTPS,
trust only actual ingress source IPs/CIDRs in `app.forwardedAllowIps`.
Set `frontend.enabled=false` for backend-only deployments.

The chart defaults to external MongoDB through `externalMongo.existingSecret`
and external HTTPS OpenBao through `openbao.address`.
Provision GCS/Pub/Sub/IAM externally and set `spool.bucket`, `spool.eventTopic`,
`spool.subscription`, `spool.silverTopic`, `spool.silverSubscription`,
`spool.parseDlqTopic`, `spool.loadDlqTopic` and `spool.leaseSeconds`;
supply a published application image and real Auth0 values. See the runbook for deployment, Secret management, and
`make helm-down`. Image builds are needed for deployments, not local Python edits.
